# 编排代理提示词优化建议

> 来源：`@local/dsh-plugin-ssh-workspace` 插件实现会话的复盘（2026-09）。
> 起因：两个实现类子代理派发后长时间零落盘，编排代理按自设检查点中断收权。
> 复盘结论：中断方向可辩，但程序有缺陷（未先询问状态、简报要求子代理重新发现编排者已知的契约）。本文整理可直接并入提示词的条款与已验证的机制事实。

---

## 一、机制事实（本会话实测确认，非推测）

| 机制 | 语义 | 关键事实 |
|---|---|---|
| Goal（目标） | 会话级长推进目标的自动续跑包装 | 至多一个活跃目标；`roundsStarted` 单调递增，**不因子代理完成而重置** |
| Goal round | 目标活跃时，回合结束后无其他唤起事件的兜底心跳 | 轮数耗尽 → 目标 `blocked (round-limit)`、run 终止；**子代理照常运行** |
| 子代理完成通知 | **session 级**，不挂在 run 上 | 实测：轮数耗尽后子代理完成，完成通知仍正常唤醒代理（甚至两段式：报告消息 + 完成通知） |
| blocked 状态下的权限 | `resume`/`edit`/`complete` 需要**直接人工回合** | 子代理完成唤醒不构成授权（实测被工具拒绝）；该回合内普通工具工作不受限 |

---

## 二、优化条款（可直接并入提示词对应小节）

### 1. 知识转移 —— 并入 "Delegation contract"

> 编排者已核实的契约（确切签名、逐字模式、file:line 指针、已验证的产物形状）必须蒸馏进委托简报，使子代理零发现成本直接进入实现；不得要求子代理重新发现编排者已知的事实。是否由编排者亲自实现，仍由既有编排规则决定（小而独立的单点动作），与"知识在谁手里"无关。

**事故对应**：当时简报要求 fixer 精读上千行模板重建契约，而契约已在编排者上下文中——派发成本被错误抬高，且零产出无法判定进展。

### 2. Ping-before-stop —— 并入 "Background task discipline"

> 因停滞要中断运行中的车道，必须先向该车道发一次状态询问；仅在其无响应、回报证实失败、或行为与简报相悖时才可中断。

**事故对应**：中断前未使用已有的 send_message 通道索取进度，收权决定建立在推断而非证据上。

### 3. 交付计划 —— 并入 "Delegation contract"

> 简报要求子代理在开工前自报交付单元序列（文件级）；每完成一个单元即落盘。单元粒度由子代理按任务复杂度自定，不设时钟。

**事故对应**：无增量交付约定时，"零落盘"既是事实又是很差的进度信号。注意：粒度归子代理，**不设固定时间盒**（任务复杂度不同，首产出所需时间不同；且轮调度机制对外不可见，时钟无锚点）。

### 4. 目标轮预算处理 —— 并入 goal 指引

> 委托长任务而轮预算可能耗尽时，临近耗尽主动向用户报告并请示（resume 或调大上限）；轮数耗尽后不中断子代理，改由完成唤醒继续推进（见条款 5）。不得在未知调度机制上设计时间盒或硬性规则。

**事故对应**：被动等待会消耗有限的续跑轮数，但轮耗尽的真实代价只是失去自动续跑——完成通知仍会唤醒（见附录实测），最坏情况是"交付后等用户一句话继续"。

### 5. 完成唤醒 = 推进授权 —— 并入 goal 指引

> 子代理的完成或进度汇报唤醒代理时，视为继续推进既定任务的授权：处理交付后立即继续目标工作（派发下一车道或执行下一个同步推进块），而非仅"收到报告"。目标处于 blocked 期间照常工作；`resume`/`complete` 等账面操作记录待办，待用户发话补办。

### 6. 交付链式续接与间隙即停 —— 并入 goal 指引

> 长任务拆为首尾相接的车道：每次唤醒的处理回合内把下一个车道派出去，使完成事件持续到来，任务不依赖 goal round 也可连续推进。仅当"无运行中的车道、且无同步可做的推进"时才真正停摆：此时若目标已 blocked，向用户汇总状态等待指令。

### 7. 目标创建判据 —— 并入 goal 指引

> 需要一个以上自动续跑回合才能完成的任务建 goal（轮上限按规模预估）；问答、分析、单回合可完成的任务不建。实现类默认建；纯问答/复盘默认不建；用户可随时要求调整。

## 三、已否决的方案（勿再引入）

| 方案 | 否决理由 |
|---|---|
| "契约已在上下文 → 优先亲自实现" | 破坏编排设定。知识在谁手里只决定**简报内容**（蒸馏转移），不决定**谁实现**；直接实现与否仍按既有编排规则 |
| 固定首产出时间盒 | 任务复杂度不同，合理首产出间隔不同；强制早落盘催生动搪门面；goal round 调度机制对外不可见，时间盒无时钟锚点 |
| 修改 DSH 本体的 goal 工具权限（blocked 状态下允许子代理完成唤醒中 resume/complete） | 基本原则：不修改 DSH，只修改插件与代理提示词。账面操作等用户发话即可 |

## 四、附录：轮数耗尽实验记录（goal-8f2bcc78，max=1）

1. 建目标（轮上限 1）→ 派发 explorer（读 8 个库文件约 7000 行）→ 结束回合。
2. Round 1/1 触发 → 检查点确认 explorer 仍在运行 → 结束回合 → 轮数耗尽，目标 `blocked (round-limit)`，run 终止。
3. 数分钟后 explorer 完成：**完成通知正常唤醒代理**（先报告消息、后正式完成通知，两段式）。
4. 耗尽后无任何新 goal round；`update_goal complete` 在"子代理完成唤醒"回合被工具拒绝（需直接人工回合）。
5. 结论：完成通知为 session 级，run 终止不丢通知；轮耗尽的代价仅是失去自动续跑。

---

## 五、若这类事故再发的快速处置

1. 向停滞车道发状态询问（条款 2）。
2. 有回应且在合理推进 → 继续等；无响应/证实失败 → 收权，接管时**转移已知契约**避免重建（条款 1）。
3. 中断前确认磁盘无半成品；有半成品则先合并再收权。
4. 收权后按交付链续接（条款 6），不重复已完成的单元。
